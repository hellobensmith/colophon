# How Scripture APIs answer the same questions

Generated by `bun conformance/run.ts`. Each column is one public API; each row is a question a caller would care about. Every API answers in its own dialect through an adapter, so this is a map of what the ecosystem does — not a scorecard, and not a pass/fail against any one implementation's endpoint shapes.

**This exists for transparency, not criticism.** Every project here is solving the same problem without a shared contract to work from, and each arrived at reasonable answers that happen not to agree. That is the cost of there being no agreed semantics, and it is paid by the people building on top. The suite scores its own author's API as a subject alongside the rest, and found a gap there too.

`n/a` means the API does not claim that capability — several take numeric book identifiers and leave reference parsing to the client, which is a design choice, not a defect. `differs` marks a defensible answer incompatible with another defensible answer. **UNSAFE** marks the sharpest case: an answer a caller cannot tell is wrong.

*Ambiguous abbreviation* — "Jo" begins Job, Joel, John, Jonah and Joshua. An API that picks one silently returns a real verse from the wrong book, and the caller has no way to detect it.

*Verse past end of chapter* — John 3 has 36 verses. Asking for verse 99 must not produce a different verse under a success status — that is a wrong answer a caller will quote.

*Chapter past end of book* — Genesis has 50 chapters. The same substitution risk as a bad verse number.

*Range across a chapter break* — Genesis 1:31–2:3 spans a chapter boundary. Support tells a caller whether it must decompose ranges itself.

*Multi-segment reference* — 1 Cor 13:4-7,13 is how the passage is normally cited. Without it a caller issues several requests and stitches the result.

*One-chapter book, both forms* — Jude has one chapter, so both `Jude 5` and `Jude 1:5` are cited in the wild. An API that accepts only one form silently mishandles the other.

*A verse the ASV omits* — The ASV prints no text at Matthew 17:21, keeping the number and a footnote. Implementations disagree on how to represent that, and a caller cannot tell which convention it is getting. No agreed answer exists, so nothing here is `safe`.

*Psalm superscription* — "A Psalm of David" is verse 1 in Hebrew and an unnumbered heading in English Bibles. An API that drops it loses text; one that folds it into verse 1 shifts every subsequent verse.

*The divine name* — The ASV prints "Jehovah" 6,887 times where most translations put "LORD". Substituting it silently changes what the edition says it is.

*Markup in verse text* — Verse text should be text. Embedded tags force every consumer to write a stripper, and each one strips differently.

*1901 typography* — The ASV prints the curly apostrophe U+2019 throughout and the ligature æ in about twenty-six proper nouns. Silently transliterating them changes the text; keeping them without folding for search makes those words unsearchable.

*Last verse of the canon* — Revelation 22:21 is the final boundary. Off-by-one errors surface here.

## What this shows

Of the 7 APIs measured, 4 do no reference parsing at all — they take numeric book identifiers and leave it to the caller. That is a legitimate choice, but it means every application built on them reimplements book names, abbreviations, ranges and bounds checking, and each one does it differently. Reference parsing is the single most duplicated piece of work in this ecosystem, and the least shared.

Among those that do parse references, the answers to identical questions diverge in ways a caller cannot see: whether an ambiguous abbreviation is refused or guessed, whether a verse the translation omits comes back empty, bracketed, or missing, whether a superscription is its own text or merged into verse 1.
